# 11. Bounded S3 retries and batch deletion

Status: proposed operational track. Inherits
[umbrella section 11](../../../SPEC-refactor.md#11-add-bounded-s3-retries-and-batch-deletion).

## Scope and implementation

Inventory SDK/provider retries before adding application retries so nested
policies cannot multiply the intended limits. Specify per-operation attempt and
elapsed-time bounds, backoff with jitter, applicable provider delays, and
cancellation behavior. Keep authentication, invalid input, missing objects, and
conditional conflicts distinct from retryable transient failures.

Reconcile an ambiguous write using its existing identity and conditional
semantics before retrying. Do not repeat a product mutation, change a conditional
write into an unconditional overwrite, or weaken create-only backup publication.

Extend the blob deletion contract to express per-object outcomes and implement
provider-supported bounded batches. A successful HTTP response can contain
individual failures. Only confirmed deletion or confirmed absence permits an
object's retirement and accounting release; retain uncertain/failed entries.
Keep local semantics and existing listing cursors compatible.

## Acceptance and delivery

Retry policy and batch deletion can land separately; each includes its callers.

- Mock throttling, transient server errors, accepted writes followed by connection
  loss, conditional conflicts, exhaustion, cancellation, and partial batch failure.
- Use a controlled clock/random source to assert total retry bounds.
- Verify mixed deletion outcomes retain the right queue rows and charges,
  including when a retry is interrupted.
- Compare request counts for bulk retirement and run local-backend regressions.
  This track does not add hosted serving or multi-writer support.
