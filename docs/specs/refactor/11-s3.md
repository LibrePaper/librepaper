# 11. Bounded S3 retries and batch deletion

Status: implemented and merged. Inherits
[umbrella section 11](../../../SPEC-refactor.md#11-add-bounded-s3-retries-and-batch-deletion).

## Scope and implementation

Inventory SDK/provider retries before adding application retries so nested
policies cannot multiply the intended limits. Specify per-operation attempt and
elapsed-time bounds, backoff with jitter, applicable provider delays, and
cancellation behavior. Keep authentication, invalid input, missing objects, and
conditional conflicts distinct from retryable transient failures.

Reconcile an ambiguous write using its existing identity and conditional
semantics before retrying. Do not repeat a product mutation, change a conditional
write into an unconditional overwrite, or weaken create-only backup publication.

Extend the blob deletion contract to express per-object outcomes and implement
provider-supported bounded batches. A successful HTTP response can contain
individual failures. Only confirmed deletion or confirmed absence permits an
object's retirement and accounting release; retain uncertain/failed entries.
Keep local semantics and existing listing cursors compatible.

## Acceptance and delivery

Retry policy and batch deletion can land separately; each includes its callers.

- Mock throttling, transient server errors, accepted writes followed by connection
  loss, conditional conflicts, exhaustion, cancellation, and partial batch failure.
- Use a controlled clock/random source to assert total retry bounds.
- Verify mixed deletion outcomes retain the right queue rows and charges,
  including when a retry is interrupted.
- Compare request counts for bulk retirement and run local-backend regressions.
  This track does not add hosted serving or multi-writer support.

## Implementation evidence

Status: implemented on `refactor/s3`. No hosted serving or multi-writer support
was added.

### Provider retry inventory

`storage/s3.rs` signs requests by hand and sends them through the shared
`reqwest` client in `http.rs`. There is no AWS SDK in the dependency tree and
`reqwest` performs no retries of its own, so the bounds in `storage/retry.rs`
are the only retry policy in the path and nothing multiplies them. The 300
second per-request client timeout is unchanged; the elapsed bound governs when
another attempt may start, not how long one request may run.

### Retry policy

`RetryLimits::IDEMPOTENT` (GET, HEAD, listing, DELETE) allows four attempts
within a 30 second scheduling budget, backing off from 100 ms with a 5 second
cap. `RetryLimits::WRITE` allows five attempts within 20 seconds from 200 ms,
because a write's attempts include the reads that reconcile it. Backoff is
exponential with jitter over the upper half of each interval, and a
`Retry-After` in delta-seconds raises the wait but never lowers it; a
provider delay longer than the remaining budget ends the operation instead of
being ignored. Both the clock and the jitter source are injected, so the tests
assert the attempt count and total wait exactly and never sleep.

Retryable: 408, 429, 500, 502, 503, 504, 509, and a request whose connection
produced no answer. Never retried, and unchanged in meaning: 401/403
(credentials), 400/405 and other 4xx (a malformed request), 404 (`NotFound`),
and 412/409 (`Conflict`). Exhaustion is reported as `Other`, never as absence
or conflict, so no caller draws a durable conclusion from an outage.
Cancellation is the ordinary async kind: backoff is a plain await point, so
dropping the operation's future stops it and issues no further request.

### Ambiguous writes

Before any write is repeated, the object is read back and compared *by bytes*
to what was sent -- an ETag is derived however a provider chooses and cannot
be predicted from the body. Identical bytes mean the write landed and its
version is returned rather than the object being mutated a second time. A
create-only write finding other bytes is a `Conflict`; an `If-Match` write
finding its expected version resends the same conditional request, finding
anything else is a `Conflict`, and finding the object gone is a `Conflict`.
The condition is never removed or weakened, so create-only backup publication
keeps its meaning. A write still unresolved when the bounds are spent is
reported as unresolved.

### Deletion contract

`BlobStore::delete_each` reports `Deleted`, `Absent`, `Failed` or `Uncertain`
per key; only the first two are `confirmed()` and may complete an object's
retirement. `delete` keeps its all-or-nothing meaning for callers that only
ask whether a whole request worked, and is now implemented on top of
`delete_each`. The default `delete_each` performs one removal per key through
`delete`, so injected/test stores stay compatible. `FsStore` answers per key
and no longer abandons the keys after a failed one; a `remove_dir` that cannot
tidy an emptied directory no longer fails the object's removal, because the
object is gone either way.

`S3Store` uses `POST ?delete` with at most 1000 keys per request, an XML body
carrying the CRC32 checksum header the API requires, and per-key verdicts read
from the 200 response. `InternalError`, `SlowDown`, `ServiceUnavailable` and
`RequestTimeout` for a key put only that key in the next attempt; other codes
are `Failed`; keys still unresolved when the bounds are spent are `Uncertain`.
A bucket that rejects the request itself (400/405/501) makes the store fall
back permanently to the per-object DELETE, so a gateway without multi-object
deletion keeps working. Listing and its continuation cursors are unchanged: a
retried page repeats the same token.

`DeletionWorker::run_once` now admits objects against the same budget and
removes them in one batch, counting only confirmed outcomes; an unconfirmed
one increments `objects_deferred`, keeps its `pending_deletes` row and keeps
its charge. Journal retirement releases `object_accounting` only on a
confirmed outcome and otherwise defers the retirement row.

### Measurements

Retiring 250 objects through `delete_each` against the mock provider:

| | requests |
| --- | --- |
| before (one DELETE per object) | 250 |
| after (one `POST ?delete`) | 1 |

Asserted in `bulk_retirement_costs_one_request_instead_of_one_per_object`,
which measures both paths against the same mock rather than quoting the
per-object figure from the old code.

### What the tests cover

`tests/s3_operations.rs` drives a raw-socket mock bucket, because the case
that matters most -- a write the provider applied and then failed to
acknowledge -- cannot be expressed as an HTTP response. Fifteen tests cover
throttling with `Retry-After`, transient 5xx on a conditional write, a
create-only write whose answer was lost (reconciled, applied exactly once), a
create-only write that finds another writer's bytes, a lost compare-and-swap,
conditional conflicts answered once, absence and 403 never retried, read and
write exhaustion inside both bounds, cancellation during backoff, a partial
failure inside a 200 `DeleteResult`, an unanswered batch leaving every key
uncertain, the per-key fallback and its memory, key escaping, and the request
count above. `storage/retry.rs` adds four unit tests for the bounds
themselves. `storage/maintenance.rs` adds
`an_unconfirmed_deletion_keeps_its_queue_row_and_its_charge`, which interrupts
one object's removal in a mixed batch and checks that its queue row and its
100 bytes of accounting survive, that the confirmed object's are released, and
that a later pass finishes it.

### Limitations

- `Retry-After` in the HTTP-date form is ignored in favour of our own bounded
  backoff, because honouring it needs our clock to agree with the provider's.
- Reconciling an ambiguous write costs one GET of the object's body. On the
  rare ambiguous path this doubles that object's bandwidth; comparing ETags
  instead would be cheaper but is not provider-independent.
- Two writers sending byte-identical bodies to one key cannot be told apart by
  reconciliation, which reports success for both. This deployment has one
  writer, and the resulting state is the same either way.
- The batch delete sends `x-amz-checksum-crc32` rather than the older
  `Content-MD5`. A gateway that accepts only `Content-MD5` falls back to the
  per-object DELETE, which is what every deployment did before this change.
- S3 answers 204 to a per-object DELETE whether or not the object existed, so
  the fallback path reports `Deleted` and never `Absent`. Both are confirmed.
